# 打包指南

产出两种安装包：Linux 的 `.deb` 与 Windows 的 `.exe` 安装器。

**顺序不能反**：先打 Worker，再打桌面端。桌面端会把 `dist-worker/` 整个作为
资源打进安装包，Worker 不存在或平台不匹配时 `src-tauri/build.rs` 会直接中断构建。

---

## 一、Linux（本机原生）

```bash
node scripts/build-worker.mjs
cd apps/desktop && pnpm exec tauri build --bundles deb
```

产物：`apps/desktop/src-tauri/target/release/bundle/deb/*.deb`（约 58MB）

---

## 二、Windows（在 Linux 上交叉构建）

配好环境之后只需要一条命令：

```bash
pnpm build:win
```

产物：`apps/desktop/src-tauri/target/x86_64-pc-windows-msvc/release/bundle/nsis/*-setup.exe`（约 33MB）

### 2.1 为什么交叉构建是可行的

这条路能走通，靠的是三个恰好成立的前提。任何一个不成立都得回到 Windows 机器上打包：

1. **SEA blob 与平台无关** —— 前提是 `useSnapshot` 与 `useCodeCache` 都为 `false`
   （`scripts/build-worker.mjs` 正是这么配的）。一旦开启，blob 会内嵌 V8 生成的
   机器码，就只能在同架构上使用。
2. **better-sqlite3 v13 把各平台预编译产物都装在 npm 包里**（`prebuilds/win32-x64.node`），
   运行时按平台挑。所以不需要在 Windows 上重新编译原生模块 —— 这原本是
   最难绕过的一环。
3. **Playwright 是纯 JS**，浏览器内核本来就是运行时下载的。

缺的只是一个 Windows 版 Node 二进制，从 nodejs.org 下载即可（脚本自动完成，
缓存在 `.worker-cache/`）。

### 2.2 环境准备（一次性）

```bash
# 1. LLVM 工具链
sudo apt-get install -y clang lld llvm

# Ubuntu 不单独提供 clang-cl，但它本就是 clang 的另一种驱动模式，
# clang 靠 argv[0] 判断，做个同名软链即可
sudo ln -sf /usr/lib/llvm-14/bin/clang /usr/bin/clang-cl

# 2. Rust 的 Windows 目标与 MSVC 交叉编译器
rustup target add x86_64-pc-windows-msvc
cargo install cargo-xwin        # 首次构建会自动下载 MSVC SDK/CRT

# 3. NSIS 安装器生成工具
sudo apt-get install -y nsis

# Tauri 交叉构建时固定去找 makensis.exe，转交给系统装的 NSIS
mkdir -p ~/.cache/tauri/NSIS
printf '#!/bin/sh\nexec /usr/bin/makensis "$@"\n' > ~/.cache/tauri/NSIS/makensis.exe
chmod +x ~/.cache/tauri/NSIS/makensis.exe
```

### 2.3 构建时的正常噪音

以下输出**不是错误**，不用管：

| 输出                                         | 原因                                                   |
| -------------------------------------------- | ------------------------------------------------------ |
| `The signature seems corrupted!`             | 官方 node.exe 带 Authenticode 签名，注入资源后自然失效 |
| `lld-link: Cannot use debug info`            | 微软发布的 `.lib` 引用了未公开的 PDB                   |
| `Cross-platform compilation is experimental` | Tauri 的例行提醒                                       |
| `-OUTPUTCHARSET is disabled`                 | NSIS 在非 Windows 上不支持该选项                       |

### 2.4 签名

安装器**未签名**。Windows 上首次运行会弹 SmartScreen「未知发布者」，
点「更多信息 → 仍要运行」即可。要消除提示需要购买代码签名证书，
在 `tauri.conf.json` 的 `bundle.windows.signCommand` 配置签名命令。

## 三、GitHub Actions

打 `v*` 标签会触发 `.github/workflows/release.yml`，在 windows-latest 与
ubuntu-22.04 两个 runner 上**原生**构建，不走交叉编译。先跑 `pnpm check`，
不过质量闸门就不出包。

本地交叉构建适合快速验证，正式发布走 CI —— 原生构建能签名，交叉构建不能。

## 四、验证产物

### 4.1 Linux

```bash
dpkg -x "…_amd64.deb" /tmp/verify
/tmp/verify/usr/bin/autojob-desktop        # 应拉起 worker 并显示界面
```

### 4.2 Windows 产物在 Linux 上的验证

**Worker 可以用 Wine 实跑**，这是最有价值的一步 —— 它能验证 SEA 注入是否成功、
Windows 版原生模块能否加载：

```bash
sudo apt-get install -y wine64 p7zip-full

7z x "…-setup.exe" -o/tmp/verify
cd /tmp/verify/worker
NODE_SKIP_PLATFORM_CHECK=1 wine64 ./autojob-worker.exe
# 期望输出：AUTOJOB_WORKER_READY <port> <token>

# 再调一个走数据库的接口，验证 win32-x64.node 真的能加载
curl -s -X POST "http://127.0.0.1:<port>/applications" \
  -H "content-type: application/json" -H "x-autojob-token: <token>" -d '{}'
```

`NODE_SKIP_PLATFORM_CHECK=1` 是因为 Wine 默认自称 Windows 7，而 Node 要求 8.1+。

**桌面端外壳无法用 Wine 验证**：Ubuntu 22.04 的 Wine 6.0 缺 `bcryptprimitives.dll`，
且 Wine 至今没有 WebView2。界面部分只能在真实 Windows 上确认。
